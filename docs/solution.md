## 과제 요약

Sendbird의 AI 에이전트 서비스 **Delight.AI**는 대시보드의 정보 구조(IA)가 다층적 계층으로 진화하고 있다.
아래 요구사항을 충족하는 대시보드 웹 서비스의 와이어프레임을 제안하는 것이 과제다.

- 제품의 계층 구조를 명확히 시각화하고, 사용자 흐름에 최적화된 레이아웃 구성
- 핵심 계층 구조 외의 세부 요소는 스켈레톤 UI로 처리해도 무방
- **복수의 Workspace와 AI Agent 선택이 가능한 초기 진입 경로** 필수 설계
- **각 Agent별 환경(Development / Staging / Production) 관리 구조** 포함

## 접근 방식

### 와이어프레임이 아닌 인터랙티브 프로토타입으로

과제는 "와이어프레임"을 요구했지만, 정적 이미지로는 계층 구조 간 **전환 흐름**과 **환경 관리의 실제 동작**을 전달하기 어렵다고 판단했다.

대신 클릭 가능한 인터랙티브 프로토타입을 구현했다. 실제 라우팅, 상태 전환, 애니메이션이 작동하므로 설계 의도를 더 명확하게 전달할 수 있다. 핵심 계층 구조와 흐름이 없는 영역은 스켈레톤 UI로 처리했다.

### 해결해야 할 핵심 문제부터 정의했다

AI 에이전트 관리 대시보드에서 사용자는 세 가지 독립적인 축을 동시에 다뤄야 한다.

| 축 | 질문 | 혼동 시 결과 |
|----|------|-------------|
| **소속** | 나는 어느 팀의 어떤 에이전트를 보고 있나? | 다른 팀의 에이전트를 수정 |
| **환경** | 지금 개발 중인 버전인가, 실서비스인가? | Production을 직접 편집하는 사고 |
| **작업** | 지금 뭘 하려는 중인가? | 맥락 전환 시 작업 손실 |

가장 위험한 혼동은 **Production 환경과 Development 환경의 혼동**이다. AI 에이전트는 코드가 아닌 언어와 논리로 작동하기 때문에, 실수로 Production 프롬프트를 수정하면 즉각 실제 사용자 경험에 영향이 간다.

이 세 축을 화면의 물리적으로 다른 공간에 배치하는 것이 설계의 출발점이었다.

```
좌측 사이드바        → 소속 (Org / Workspace / Agent 탐색)
좌측 파이프라인 패널 → 환경 (Dev / Staging / Production 선택)
우측 Console 탭      → 작업 (Overview / Build / Test / Evaluate)
```

## Claude Code 활용 방식

### 프로토타입 구현에 Claude Code를 선택한 이유

프로토타입을 Figma가 아닌 실제 코드로 구현하되, 직접 코딩이 아닌 **Claude Code(AI 코딩 에이전트)를 주 구현 도구로 활용**했다. 설계 의사결정에 집중하면서 구현 속도를 극대화하기 위해서다.

단순히 코드 생성을 요청하는 것을 넘어, AI가 일관된 품질로 반복 작업할 수 있는 **실행 환경(Harness)을 설계하는 것**이 핵심이었다.

> "코드를 직접 작성하는 개발자"에서 "코드를 작성하는 AI를 관리하는 환경 설계자"로의 전환. 이것이 Harness Engineering이다.

### MD 파일 분리 전략

AI에게 작업을 맡기기 전에 세 종류의 문서를 먼저 작성했다. 각 문서는 서로 다른 역할을 담당한다.

**AGENTS.md — 사전 제약**

AI가 코드를 작성하기 전에 반드시 읽어야 할 전제 조건을 담는다. "이 프로젝트의 Next.js는 일반 버전과 다를 수 있으므로 코드를 작성하기 전 관련 가이드를 먼저 읽어라"와 같이, AI가 잘못된 가정으로 시작하는 것을 막는 첫 번째 관문이다.

**DESIGN.md — 스타일 가이드**

색상 팔레트, 타이포그래피, 컴포넌트 패턴, 인터랙션 원칙을 정의한다. AI가 UI를 구현할 때 디자인 시스템에서 이탈하지 않도록 하는 참조 문서다. 이 파일이 없으면 AI는 매 작업마다 임의의 색상과 간격을 선택한다.

**CLAUDE.md — 프로젝트 규칙 (린터 역할)**

AI가 작업할 때 반드시 지켜야 할 명시적 규칙을 담는다. 예를 들어:
- URL 구조 변경 금지
- 버전은 반드시 `formatVersion()` 함수를 통해 표시
- 환경별 색상 시스템 (변경 금지)
- 알림은 항상 탭 콘텐츠 최상단에 배치
- Production/Staging Build 탭 읽기 전용 강제

규칙이 없으면 AI는 매 작업마다 다른 판단을 내린다. 규칙이 있으면 AI는 작업의 "방향"만 지시받고 "방식"은 스스로 규칙 내에서 해결한다.

### 워크플로우

```
1. 설계 의사결정 (사람)
        ↓
2. CLAUDE.md / DESIGN.md에 규칙 반영
        ↓
3. Claude Code에 구현 지시
        ↓
4. 브라우저에서 결과 확인 (사람)
        ↓
5. 피드백 → 반복
```

**AI에게 맡긴 것**: 컴포넌트 코드, CSS, 애니메이션, 반응형 처리

**직접 결정한 것**: 정보 우선순위, 계층 구조, 환경 분리 방식, 알림 배치 원칙, 색상 시스템

규칙 문서에 없는 미묘한 판단(간격 조정, 애니메이션 타이밍, 정보 우선순위)은 브라우저에서 직접 확인하고 피드백하는 루프에서 정제했다.

## 화면별 UX 설계 근거

### Org Home — "지금 우리 조직에 무슨 일이 일어나고 있나?"

로그인 직후 처음 보는 화면이다. 이 화면에서 사용자가 해야 할 일은 크게 세 가지다.

1. **전체 현황 파악** — 오늘 대화량은 어떤가, CSAT는 괜찮은가, 알림이 있는가
2. **문제 에이전트 확인** — 어디서 경고가 발생했는가, 얼마나 심각한가
3. **목적지로 이동** — 특정 Workspace나 Agent로 빠르게 진입

이 세 가지를 순서대로 처리할 수 있도록 **좌우 2컬럼 레이아웃**을 선택했다.

좌측은 흐름형 정보다. Overview KPI 카드(Sparkline 포함) → Workspace 목록 → Agent 목록 순서로 내려간다. 위에서 아래로 읽으면 조직 전체 수치 → 어느 팀 → 어느 에이전트 순으로 드릴다운하는 자연스러운 시선 흐름이 만들어진다.

우측은 지금 당장 처리해야 할 것이다. Active Issues는 전체 Workspace에 걸친 경고 에이전트를 severity 순으로 보여준다. 스크롤 없이 눈에 들어오게 하기 위해 우측 고정 컬럼을 선택했다. 좌측 리스트를 스크롤하더라도 우측 이슈 패널은 항상 시야에 남는다.

KPI 카드에 Sparkline 차트를 넣은 이유는 숫자 하나만으로는 "좋은 건지 나쁜 건지"를 판단하기 어렵기 때문이다. 7일 추세가 함께 보이면 "3,842건"이라는 숫자가 늘어나는 추세인지 꺾이는 추세인지 즉시 판단할 수 있다.

Workspace 카드에 멤버 아바타 스택과 에이전트 수를 하단에 배치한 것은 "이 공간에 누가 있고 얼마나 운영 중인가"라는 맥락을 카드 안에서 바로 전달하기 위해서다.

---

### Workspace Home — "이 팀의 에이전트들은 지금 어떤 상태인가?"

Org Home이 조직 전체의 조감도라면, Workspace Home은 **한 팀의 운영 현황판**이다. 같은 팀 내에서 에이전트 간 상태를 비교하고, 특정 에이전트로 진입하는 것이 주 사용 패턴이다.

상단 KPI 카드는 해당 Workspace에 한정된 수치다. Org Home의 KPI와 동일한 포맷을 유지해 계층이 달라져도 읽는 방식이 같다. 사용자가 계층을 이동할 때마다 새로운 UI 패턴을 학습할 필요가 없다.

에이전트 목록은 **Grid / List 두 가지 뷰**를 제공한다. Grid는 에이전트가 많지 않을 때 각 카드의 상태를 시각적으로 훑기 좋다. List는 에이전트가 많아질수록 밀도 있게 비교하기 좋다. 팀 규모와 에이전트 수에 따라 사용자가 선택할 수 있도록 했다.

각 에이전트 카드와 리스트 로우에는 **파이프라인 상태 도트**가 표시된다. Development / Staging / Production 각 환경에 배포됐는지를 점 세 개로 요약한다. 이 세 점만 봐도 "이 에이전트가 실서비스에 올라가 있는지"를 한눈에 알 수 있다. 경고가 발생한 환경의 도트는 PulseDot(펄스 애니메이션)으로 교체되어 어느 환경에서 문제가 발생했는지 즉시 식별된다.

---

### Agent Home — "이 에이전트를 개발하고, 검증하고, 배포한다"

에이전트 페이지는 **집중 작업 공간**이다. Workspace Home에서 에이전트를 선택하는 순간 사이드바가 자동으로 접히는 이유가 여기 있다. "지금부터는 다른 곳을 탐색하는 게 아니라 이 에이전트에 집중한다"는 모드 전환을 공간으로 표현한다.

화면은 크게 **파이프라인 패널(좌)**과 **Console(우)**로 나뉜다.

파이프라인 패널은 환경 선택 도구다. Development / Staging / Production 세 카드가 수직으로 나열되고, 선택한 카드에 따라 Console의 모든 정보가 해당 환경 기준으로 바뀐다. 환경 간 이동이 잦은 운영자에게 항상 고정 위치에 있는 패널이 탭보다 빠르다. 각 카드는 배포 버전, 건강 상태, 마지막 배포자를 함께 표시한다 — 환경을 선택하기 전에 이미 "이 환경에 무엇이 올라가 있는지"를 알 수 있다.

Console의 탭 구조는 **에이전트의 생애주기**를 따른다.

| 탭 | 역할 | 생애주기 단계 |
|----|------|-------------|
| Overview | 현재 상태와 성과 모니터링 | 운영 |
| Build | 프롬프트·모델·지식베이스 편집 | 개발 |
| Test | 직접 대화하며 동작 검증 | 검증 |
| Evaluate | 실제 대화 데이터 기반 품질 분석 | 개선 |

개발 → 검증 → 운영 → 개선의 순환이 왼쪽에서 오른쪽으로 탭 순서에 반영된다. 사용자는 지금 어느 단계에 있는지 탭 위치로 직관적으로 파악한다.

Build 탭 내부 섹션 네비게이션을 좌측 사이드가 아닌 상단 탭으로 처리한 것은 이미 3분할된 화면에서 추가 분할을 피하기 위해서다. 화면이 좁아질수록 실제 편집 영역이 압박받기 때문이다.

## 주요 UX 결정 및 근거

### 1. 이슈가 발생하면 즉각 대응할 수 있는 경로 설계

AI 에이전트 운영에서 **Production 이슈는 발견 즉시 처리해야 한다**. 그런데 기존의 대시보드 설계 방식은 대부분 "알림 → 별도 화면 이동 → 에이전트 찾기 → 환경 전환 → 문제 확인"처럼 여러 단계를 요구한다.

이 프로젝트에서는 이슈 발견부터 처리까지의 경로를 최소화하는 데 집중했다.

**Org Home의 Active Issues 패널**은 전체 Workspace에 걸쳐 경고 중인 에이전트를 severity 순으로 노출한다. 리스트의 각 항목은 바로 해당 에이전트 페이지로 이동하는 링크다. 로그인 직후 첫 화면에서 "어디에 문제가 있고, 그게 얼마나 심각한가"를 파악하고 한 번의 클릭으로 처리 화면에 도달할 수 있다.

**PulseDot(펄스 애니메이션 점)**은 경고 상태인 에이전트의 파이프라인 위치에 표시된다. 정적 아이콘이 아닌 움직이는 표시를 쓴 이유는 "지금 이 순간에도 문제가 진행 중임"을 시각적으로 전달하기 위해서다. Workspace 카드, 에이전트 리스트, 파이프라인 패널 등 계층의 모든 단계에서 일관되게 나타나기 때문에 어느 화면에 있어도 이슈를 놓치지 않는다.

**알림의 절대적 우선순위**: 경고·정보 알림은 항상 탭 콘텐츠 최상단에 위치한다. KPI 카드나 에이전트 정보 아래에 오지 않는다. CSAT가 좋아 보여도 경고가 있다면 그것을 먼저 봐야 한다. 배치 순서가 중요도를 표현한다. 또한 알림은 `alertEnv` 필드로 해당 환경에만 노출된다 — Development를 보고 있는 사람에게 Production 경고를 보여주면 혼란이다.

### 2. Production/Staging Build 탭 읽기 전용 강제

Production 환경의 Build 탭은 편집 불가다. 편집 버튼이 없고, 읽기 전용 배너가 표시되며, 배경색이 달라진다.

**설계 논리**: 권한 팝업은 사용자가 무시할 수 있는 경고다. 읽기 전용 UI는 선택지 자체가 없다. "실수는 막는 것이 아니라 일어날 수 없게 해야 한다."

변경은 항상 Development에서 시작해 Promote 흐름을 통해서만 상위 환경에 반영된다. 이 단방향 흐름이 모든 변경을 추적 가능하게 만든다.

### 3. 사이드바 자동 접힘 — 모드 전환의 시각화

에이전트 페이지 진입 시 사이드바가 자동으로 접힌다. 편의 기능이 아니라 **"지금부터는 이 에이전트에 집중한다"는 모드 전환**을 공간으로 표현하는 것이다.

닫힐 때 콘텐츠 fade out(120ms) → width 축소(220ms), 열릴 때 width 확장 → 콘텐츠 fade in(180ms delay). 2단계 애니메이션은 내용이 사라진 후 공간이 정리되는 자연스러운 순서를 만든다.

### 4. Promote 버튼의 위치

Promote 버튼은 각 탭 콘텐츠 영역의 하단 좌측에 있다.

만약 Promote 버튼이 파이프라인 패널에 있었다면, 사용자는 Build도 Test도 하지 않고 습관적으로 누를 수 있다. 탭 콘텐츠 안에 있다는 것은 "이 탭에서 충분히 작업한 후에 다음 단계로 가라"는 암묵적 신호다.

### 5. Model 선택 — 드롭다운 → 2×2 카드 그리드

AI 에이전트의 모델 선택은 단순 값 선택이 아닌 **비교하며 결정하는 행위**다. 드롭다운은 열어야만 선택지를 볼 수 있다. 카드 그리드는 모든 선택지를 동시에 보여주고, 모델 이름·제공사·특성을 함께 표시한다. 선택지가 비교를 요구하는 상황에서는 펼쳐서 보여주는 것이 옳다.

## 현재 한계 및 향후 과제

| 항목 | 현재 상태 | 필요한 것 |
|------|-----------|-----------|
| Promote Dialog | 버튼 위치만 확립 | Diff 비교, 체크리스트, 확인 플로우 |
| 실시간 알림 | Mock 데이터 하드코딩 | 실시간 모니터링 데이터 연결 |
| Evaluate 탭 | KPI 카드 + 설명 수준 | 세션 분석, Top Failed Intent, 트렌드 차트 |
| 에이전트 비교 뷰 | 없음 | Dev vs Production Diff 나란히 보기 |

## 마무리

이 과제에서 해결하려 한 핵심 문제는 하나다.

> **하나의 화면에서 소속·환경·작업이라는 세 독립적인 축을 동시에, 혼동 없이 다루게 하는 것.**

이를 위해 각 축을 물리적으로 다른 공간에 배치하고, 가장 위험한 실수(Production 직접 편집)는 선택지 자체를 없애는 방식으로 막았다. 이슈 발생 시 즉각 대응할 수 있는 경로를 계층 전반에 일관되게 설계했다.

Claude Code는 이 설계를 빠르게 구현하는 도구였고, CLAUDE.md · DESIGN.md · AGENTS.md는 AI가 설계 원칙을 이탈하지 않도록 잡아주는 하네스였다.
