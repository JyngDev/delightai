# ADR-002: Agent 카드의 복합 상태를 어떻게 표시할 것인가

> **ADR 번호**: 002
> **제목**: Agent 카드 최상단의 복합 상태 라벨링
> **상태**: Accepted (채택됨)
> **결정일**: 2026-04-22
> **결정자**: UX Design
> **관련 문서**: ADR-001 (Agent 환경 표시), WORKSPACE_HOME_INFO_GUIDE.md
> **선행 ADR**: ADR-001에서 결정된 "Production 중심, Dev/Staging 보조" 원칙의 확장

---

## 📌 컨텍스트 (Context)

### 배경

ADR-001에서 Agent 카드의 환경 표시 방식을 "Production 중심, Dev/Staging 보조 표시"로 결정했다. 그러나 이 결정을 실제 구현하려 하자, 더 근본적인 문제가 드러났다.

**한 Agent는 동시에 여러 상태에 있을 수 있다.**

예를 들어 Support Bot의 현재 상태가 다음과 같다고 하자.

```
Production:  v0.38 (실서비스 운영 중)
Staging:     (없음)
Development: v0.42 (개발자가 새 기능 작업 중)
```

이 Agent를 한 마디로 어떻게 표현해야 하는가?

- "Production 단계"? → Dev에서 활발히 작업 중인데 부정확
- "Development 단계"? → 실서비스 중인데 부정확
- **"운영 중이면서 개발 중"** → 이게 정확한 상태

이 "복합 상태"를 Agent 카드에 어떻게 시각화할 것인가에 대한 결정이 필요하다.

### 이 결정이 왜 중요한가

**환경이 "단계(stage)"가 아니라 "공간(space)"이라는 제품의 본질**이 걸린 결정이다.

- 선형 단계 모델: Dev → Staging → Prod → 끝
- 실제 모델: Dev ↔ Staging ↔ Prod (셋이 동시에 존재하며 지속적으로 갱신됨)

Agent는 첫 배포 이후 **대부분의 시간을 "여러 환경에 동시 존재"하는 상태로 보낸다**. 따라서 카드의 상태 표시가 이 본질을 반영해야 한다.

### 결정이 미치는 범위

- Workspace Home의 Agent 카드 (본 결정의 1차 적용처)
- Organization Home(Entry 화면)의 Agent 미니 표시
- Agent 검색 결과 리스트
- 각종 Agent 목록 뷰의 상태 아이콘

---

## 🎯 결정 (Decision)

### 채택안: **복합 상태 라벨을 최상단에 복수 표시 (Composite State Badge)**

Agent 카드 최상단에 Agent 이름 **위에** 상태 라벨을 배치하되, 동시에 여러 라벨이 병기될 수 있음을 허용한다.

### 구체 규칙

#### 규칙 1: 상태 라벨의 정의

5가지 기본 상태 라벨을 정의한다.

| 라벨                  | 색상       | 조건                                                 |
| --------------------- | ---------- | ---------------------------------------------------- |
| 🟢 **LIVE**           | Green      | Production 환경에 배포되어 실서비스 중               |
| 🟡 **IN REVIEW**      | Amber      | Staging 환경에 Prod보다 새 버전이 있음 (QA/검증 중)  |
| 🔵 **IN DEVELOPMENT** | Blue       | Dev 환경에 Staging/Prod보다 새 버전이 있음 (개발 중) |
| ⚫ **ARCHIVED**       | Gray       | Agent가 아카이브됨 (서비스 중단)                     |
| ⚪ **NOT DEPLOYED**   | Light Gray | 어느 환경에도 배포되지 않음 (신규 생성 직후)         |

#### 규칙 2: 복수 라벨 허용

한 Agent는 동시에 여러 라벨을 가질 수 있다.

- Prod 운영 중 + Dev 작업 중 → `🟢 LIVE · 🔵 IN DEVELOPMENT`
- Prod 운영 중 + Staging 검증 중 + Dev 작업 중 → `🟢 LIVE · 🟡 IN REVIEW · 🔵 IN DEVELOPMENT`

#### 규칙 3: 라벨의 우선순위

복수 라벨을 **왼쪽부터 우선순위 순**으로 배치한다.

```
LIVE → IN REVIEW → IN DEVELOPMENT
```

사용자가 좌측부터 읽을 때 **가장 중요한 상태(실서비스)를 먼저** 인지하도록.

예외:

- `ARCHIVED`는 단독으로만 표시 (다른 라벨과 병기 안 됨)
- `NOT DEPLOYED`는 `IN DEVELOPMENT`와 배타적 (개발 중이면 NOT DEPLOYED 대신 IN DEVELOPMENT)

#### 규칙 4: "활동 없는 환경"은 라벨에서 제외

환경에 버전이 있더라도 **Prod와 같은 버전이면 별도 상태로 표시하지 않는다**.

| 상황                                              | 라벨 표시                                  |
| ------------------------------------------------- | ------------------------------------------ |
| Dev = Staging = Prod (모두 v0.38)                 | 🟢 LIVE (안정)                             |
| Dev = Staging = Prod, 하지만 Dev에 미저장 수정 중 | 🟢 LIVE · 🔵 IN DEVELOPMENT                |
| Prod v0.38, Staging v0.38, Dev v0.42              | 🟢 LIVE · 🔵 IN DEVELOPMENT                |
| Prod v0.38, Staging v0.41, Dev v0.42              | 🟢 LIVE · 🟡 IN REVIEW · 🔵 IN DEVELOPMENT |

핵심: **"Prod와 다른 버전이 있는 환경"만 별도 상태 라벨로 인정**.

#### 규칙 5: 최대 표시 개수 제한

최대 3개까지만 표시한다. 위의 5가지 라벨 정의상 실제로 3개가 한계이므로 자연스럽게 지켜진다.

#### 규칙 6: 시각 처리 원칙

- **색상 + 텍스트 병행 필수** (접근성, 흑백 환경 대응)
- 각 라벨은 뱃지(pill) 형태
- 이름 위에 별도 라인으로 배치
- 라벨 간 구분자는 점(·) 또는 여백
- 각 라벨에 마우스 호버 시 툴팁으로 의미 설명

#### 규칙 7: 배치 위치

Agent 이름 **위**(최상단)에 배치한다. 이유:

1. 여러 카드를 나열했을 때 **상태별 패턴 인식**이 쉬움
2. **시간에 따라 변하는 정보는 상단**, 고정 정보(이름)는 그 아래가 자연스러움
3. 사용자의 첫 스캔 시선이 닿는 위치

## 🔄 검토한 대안들 (Alternatives Considered)

### 대안 A: 단일 "지배적 상태"만 표시 ❌

가장 중요한 상태 하나만 골라서 표시.

```
Production에 있으면 → 🟢 LIVE
Staging까지만 있으면 → 🟡 IN REVIEW
Dev만 있으면 → 🔵 IN DEVELOPMENT
```

**장점**:

- 시각적으로 가장 깔끔
- 스캔 속도 최고

**단점**:

- **"운영 중이면서 개발 중"이라는 복합 상태를 표현 불가**
- 한 라벨로 축약하면 정보 손실 발생
- 사용자가 "지금 건드려도 되나?"를 한눈에 판단할 수 없음 (LIVE인데 Dev에서 작업 중이면 건드리면 안 됨)

**기각 이유**: 이 제품의 본질(환경 공존)을 표현하지 못함. 정보 손실이 크다.

### 대안 B: 라벨 없이 환경 뱃지만 표시 ❌

상태 라벨 개념 자체를 제거하고, 각 환경의 배포 여부만 뱃지로 표시.

```
[DEV] [STG] [PROD]  ← 배포된 환경만 색상 강조
```

**장점**:

- 환경 정보가 직접 드러남
- 구현 단순

**단점**:

- **"상태"와 "환경"은 다른 차원**: 뱃지만으로는 "지금 작업 중인가, 안정 상태인가"를 알 수 없음
- Prod에 있는데 Dev에서 새 작업 중인 상황과, 완전 안정 상태를 구분 못 함
- 사용자가 환경 뱃지를 해석해야 하는 인지 부하

**기각 이유**: 환경의 배포 여부(fact)와 그 해석(state)은 다른 레이어. 해석을 사용자에게 미루는 건 나쁜 UX.

### 대안 C: "파이프라인 진행률" 표시 ❌

Agent를 파이프라인의 진행도로 표현.

```
▓▓▓░░  Dev 통과
▓▓▓▓░  Staging 검증 중
▓▓▓▓▓  Prod 도달
```

**장점**:

- 시각적으로 재미있음
- 파이프라인 흐름 직관적

**단점**:

- **선형 진행 모델 강조**: 실제로는 순환 사이클인데 선형처럼 보임
- "Prod 있으면서 Dev 작업 중"을 어떻게 표현할지 모호
- 공간 차지 큼

**기각 이유**: 진행률 은유는 이 제품의 "순환적 사이클"에 맞지 않음.

### 대안 D: 최상단 없이 부가 정보 영역에만 표시 ❌

상태를 카드 최상단이 아닌 **하단의 부가 정보**로 표시.

```
🤖 Support Bot
Production v0.38
💬 12,483 · 😊 4.6
⏸ Dev에서 작업 중          ← 하단 부가 정보
```

**장점**:

- 이름·핵심 지표가 강조됨
- 공간 배치 유연

**단점**:

- **카드 여러 장을 스캔할 때 상태 패턴 인식 어려움** (위치가 하단이면 시선이 가닿지 않음)
- 중요도가 낮게 느껴짐

**기각 이유**: "지금 상태"는 사용자의 첫 번째 질문이므로 최상단이 맞다.

### 대안 E: 아이콘만 사용 (텍스트 없이) ❌

라벨을 색깔 점이나 아이콘으로만 표현.

```
🟢 🔵          ← 이것만 표시
🤖 Support Bot
```

**장점**:

- 공간 최소화
- 시각적 간결

**단점**:

- **접근성 문제**: 색맹, 스크린리더 대응 불가
- 각 아이콘 의미 학습 필요
- 처음 보는 사용자가 해석 불가

**기각 이유**: 접근성은 타협 불가한 기준.

## 🎯 결정의 근거 (Rationale)

### 1. 제품 본질과 UI의 일치

Delight.ai의 핵심 가치는 **"환경이 분리되어 공존하는 Agent 관리"**다. 이 본질을 가장 직접적으로 표현하는 것이 "복합 상태"다.

한 Agent가 여러 상태에 있을 수 있다는 사실을 UI가 거짓 없이 표현해야 사용자가 제품을 올바르게 이해한다.

### 2. 사용자의 첫 질문에 바로 답

Workspace Home에서 사용자가 Agent 카드를 볼 때 **가장 먼저 하는 질문**은 이것이다.

> "이 Agent, 지금 어떤 상태야?"

채택안은 이 질문에 **최상단에서 즉시** 답을 준다. 카드의 나머지 정보(이름, 지표, 버전)는 이 질문에 대한 답을 보완하는 맥락이다.

### 3. 복합성을 피하지 않고 정면으로 다룸

대안 A(단일 상태)는 복합성을 **회피**했다. 채택안은 복합성을 **직시**한다.

제품 사용자(Builder, Validator, Operator, Admin)는 이미 "Dev/Staging/Prod가 독립적"이라는 개념을 이해하고 있다. 그들에게 "LIVE이면서 IN DEVELOPMENT"는 자연스러운 개념이지, 복잡한 개념이 아니다.

### 4. 시각적 복잡도는 규칙으로 통제됨

복수 라벨이 UI를 복잡하게 만들 수 있다는 우려는 규칙 4(idle 환경 제외)와 규칙 5(최대 3개)로 통제한다. 실제로 3개 라벨이 동시에 뜨는 경우는:

- 매우 활발한 개발 팀
- 한 Agent에 Prod + Staging 검증 + Dev 작업이 동시 진행

이런 상황 자체가 드물고, 드문 만큼 **사용자가 주목해야 할 중요한 순간**이므로 3개 라벨이 오히려 도움이 된다.

### 5. 스캔 패턴 최적화

여러 Agent 카드를 한 화면에 나열했을 때, 최상단 라벨이 **같은 위치**에 있으면 사용자의 눈이:

```
카드 1: 🟢 LIVE
카드 2: 🟢 LIVE · 🔵 IN DEVELOPMENT   ← 여기 주목
카드 3: 🟢 LIVE
카드 4: 🔵 IN DEVELOPMENT             ← 신규
```

이런 패턴을 빠르게 인식할 수 있다. 지배적 상태(대안 A)로는 이 수준의 변별이 어렵다.

### 6. ADR-001과의 일관성

ADR-001에서 결정한 "Production 중심, Dev/Staging 보조"와 일치한다. LIVE 라벨이 우선순위상 가장 먼저 오고, IN REVIEW와 IN DEVELOPMENT는 그 뒤에 붙는 보조 라벨로 기능한다.

## 📊 적용 예시

### 케이스 1: 안정 운영 (Prod만, 수정 없음)

실제 상황: Prod v0.38, Staging 없음, Dev에 변경 없음.

```
🟢 LIVE
🤖 Support Bot
고객 지원 문의 처리

Production v0.38
💬 12,483 (7d) · 😊 4.6

Last edit: Jiyong, 3w ago
```

**해석**: 안정적으로 운영 중, 최근 작업 없음.

### 케이스 2: 운영 중 + 개발 중 (가장 흔한 상태)

실제 상황: Prod v0.38, Staging 없음, Dev v0.42.

```
🟢 LIVE · 🔵 IN DEVELOPMENT
🤖 Support Bot
고객 지원 문의 처리

Production v0.38
💬 12,483 (7d) · 😊 4.6

Dev v0.42 (2h ago by Jiyong)

Last edit: Jiyong, 2h ago
```

**해석**: 실서비스 중이면서 다음 버전 개발 중. Dev에서 작업 중임을 주목.

### 케이스 3: 운영 중 + 검증 중 + 개발 중 (파이프라인 full)

실제 상황: Prod v0.38, Staging v0.41, Dev v0.42.

```
🟢 LIVE · 🟡 IN REVIEW · 🔵 IN DEVELOPMENT
🤖 Support Bot
고객 지원 문의 처리

Production v0.38
💬 12,483 (7d) · 😊 4.6

Staging v0.41 (QA 중)
Dev v0.42

⏸ Staging에서 2일째 대기

Last edit: Jiyong, 2h ago
```

**해석**: 파이프라인이 활발히 돌아가는 중. Staging 지연 신호 주목.

### 케이스 4: 신규 Agent (개발 초기)

실제 상황: Dev v0.01만 있음.

```
🔵 IN DEVELOPMENT
🤖 Onboarding
신규 가입 안내

Not deployed

Dev v0.01 (5d ago by David)

Last edit: David, 5d ago
```

**해석**: 아직 어디에도 배포되지 않은 개발 초기 Agent.

### 케이스 5: 첫 배포 준비 중

실제 상황: Dev v0.01 = Staging v0.01, Prod 없음.

```
🟡 IN REVIEW
🤖 New Bot
설명

Not deployed to Production
Staging v0.01 (검증 중)

Last edit: Sarah, 1d ago
```

**해석**: 검증 완료되면 첫 배포.

### 케이스 6: 아카이브

실제 상황: 서비스 중단된 Agent.

```
⚫ ARCHIVED
🤖 Legacy Bot
(회색 처리된 설명)

Was in Production · 이전 v0.25
Archived 2026-03-01 by Admin
```

**해석**: 더 이상 운영되지 않음. 히스토리 보존용.

## 🔀 결과 및 영향 (Consequences)

### 긍정적 영향

- **제품 본질과 UI가 일치**: 환경 공존이라는 핵심 가치가 최상단에 드러남
- **사용자의 첫 질문에 즉시 답**: "이 Agent 지금 어때?"
- **여러 카드 비교·스캔 시 패턴 인식 용이**
- **"건드려도 되는가"의 판단이 명확**: LIVE 중에 작업 중인 걸 알면 조심
- **모든 페르소나가 자신의 관심 상태를 즉시 발견**

### 부정적 영향 (트레이드오프)

- **구현 복잡도 증가**: 상태 판정 로직이 5가지 케이스 × 버전 비교 로직 필요
- **디자인 일관성 관리 비용**: 복수 라벨 배치 규칙이 엄격해야 유지됨
- **신규 사용자 학습 필요**: LIVE / IN REVIEW / IN DEVELOPMENT 개념 학습
- **시각 공간 사용 증가**: 단일 라벨 대비 최대 3배의 가로폭 필요

### 후속 작업 필요

1. **WORKSPACE_HOME_INFO_GUIDE.md §4.2 카테고리 2 재작성**
   - 기존 "환경별 뱃지 표시" → "복합 상태 라벨 + 버전 정보"로 변경

2. **상태 판정 로직 구체화 (별도 기술 문서)**
   - 입력: Agent의 각 환경별 버전, 배포 여부, Agent 상태 (active/archived)
   - 출력: 라벨 배열 (예: `['LIVE', 'IN_DEVELOPMENT']`)
   - 판정 알고리즘 의사코드 필요

3. **라벨 디자인 토큰 정의**
   - 각 라벨의 색상, 뱃지 스타일
   - 라이트/다크 모드 변형

4. **툴팁 콘텐츠 작성**
   - 각 라벨 호버 시 노출될 설명 문구
   - 예: "LIVE: 이 Agent는 현재 Production 환경에서 실사용자에게 서비스되고 있습니다"

5. **접근성 대응**
   - 색맹 대응 패턴 (색상 외 기호/텍스트 구분)
   - 스크린 리더 읽기 순서 (`aria-label`)

6. **다국어 라벨 검토**
   - LIVE / IN REVIEW / IN DEVELOPMENT의 한국어 대응
   - 운영 중 / 검증 중 / 개발 중 ?
   - 영문 유지 vs 번역 결정 필요

### 모니터링 지표

이 결정이 옳았는지 검증할 지표:

- **첫 진입 후 카드 → Agent 전환까지 소요 시간**: 상태 파악이 빠를수록 감소
- **잘못된 환경에서의 편집 사고 발생률**: LIVE 표시로 경각심이 생기면 감소 예상
- **"이 Agent 지금 어떤 상태예요?" 류 고객 문의 수**: 라벨이 명확하면 감소
- **사용자 테스트에서 복합 상태 해석 성공률**: 신규 사용자가 `LIVE · IN DEVELOPMENT`를 올바로 해석하는지

### 위험 요소

- **라벨 개념이 과하게 복잡해질 위험**: 향후 "IN MIGRATION", "IN ROLLBACK" 등 추가 라벨 요구가 생길 수 있음. 추가할 때마다 이 ADR 개정 필요.
- **색상 과다**: 3가지 색 동시 표시가 특정 디자인 테마에서 충돌할 수 있음.

### ADR-001과의 관계 (선행)
