# ADR-003: Workspace Home의 뷰 모드를 어떻게 설계할 것인가

> **ADR 번호**: 003
> **제목**: Agent 중심 Grid vs 환경 중심 Pipeline — 뷰 모드 병존 전략
> **상태**: Accepted (채택됨)
> **결정일**: 2026-04-22
> **결정자**: UX Design
> **관련 문서**: ADR-001, ADR-002, WORKSPACE_HOME_INFO_GUIDE.md
> **선행 ADR**: ADR-001 (환경 표시 우선순위), ADR-002 (복합 상태 라벨)

---

## 📌 컨텍스트 (Context)

### 배경

ADR-001과 ADR-002에서 Workspace Home의 Agent 카드 표시 방식을 결정했다. 그 결정은 **Agent 중심의 그리드 레이아웃**을 전제로 한 것이었다.

```
[Agent Card] [Agent Card] [Agent Card]
[Agent Card] [Agent Card] [Agent Card]
```

각 카드 안에 환경 정보를 압축해서 담는 방식. 카드 하나 = Agent 하나.

하지만 이 구조에는 근본적 대안이 존재한다는 것이 추가 논의에서 드러났다.

**Jira·Trello 스타일의 칸반 보드처럼, 환경을 컬럼으로 두고 Agent를 그 안에 카드로 배치하는 방식.**

```
┌ DEVELOPMENT ┬ STAGING ┬ PRODUCTION ┐
│ [Agent A]   │[Agent A]│ [Agent A]  │
│ [Agent B]   │         │ [Agent B]  │
│ [Agent C]   │         │            │
└─────────────┴─────────┴────────────┘
```

이 제안은 Agent 중심 그리드의 대체안으로 제시되었고, 본 ADR은 두 접근의 관계를 정리한다.

### 이 결정이 왜 중요한가

**같은 데이터(Agent들의 환경별 상태)를 완전히 다른 두 가지 관점으로 볼 수 있다는 사실**이 드러났다.

- **Agent 중심 (Grid)**: "우리 팀에 어떤 Agent들이 있고, 각 Agent는 어떤 상태인가"
- **환경 중심 (Pipeline)**: "우리 파이프라인의 각 단계에 무엇이 있고, 어떻게 흘러가는가"

두 관점 모두 유효하며, 각자 해결하는 문제가 다르다. 하나를 선택하고 다른 하나를 포기하는 것은 **특정 페르소나와 특정 작업 맥락을 희생**하는 결정이 된다.

### 결정이 미치는 범위

- Workspace Home의 기본 레이아웃 구조
- 향후 Organization Home, Agent 검색 결과에도 확장 가능
- Promote·Rollback 같은 환경 간 이동 작업의 UX 흐름
- 모바일/태블릿에서의 반응형 전략

## 🎯 결정 (Decision)

### 채택안: **Grid 기본 + Pipeline 선택 가능 (뷰 모드 병존)**

Workspace Home에 **3가지 뷰 모드**를 제공하고, 사용자가 전환할 수 있게 한다.

| 뷰 모드      | 아이콘 | 기본 여부 | 핵심 강점                               |
| ------------ | ------ | --------- | --------------------------------------- |
| **Grid**     | ▦      | ✅ 기본값 | Agent 포트폴리오 한눈에, 지표 밀도 높음 |
| **List**     | ☰     |           | 다수 Agent 비교·스캔                    |
| **Pipeline** | ⫼      |           | 파이프라인 흐름과 환경별 부하 파악      |

### 구체 규칙

#### 규칙 1: 기본 뷰는 Grid

새 사용자가 Workspace Home에 처음 진입하거나, 명시적 설정이 없는 상태에서는 **Grid 뷰로 시작**한다.

이유:

- Workspace Home에서 사용자의 **첫 번째 질문**("어떤 Agent들이 있지?")에 Agent 중심 뷰가 가장 직접 답함
- Pipeline은 **특정 업무 맥락**(파이프라인 점검)에서 유용하나 항상 필요한 것이 아님
- 신규 사용자의 학습 곡선을 낮추기 위함

#### 규칙 2: 사용자 선택은 기억됨

사용자가 Pipeline 또는 List로 전환한 경우, 그 선택은 **해당 Workspace 범위에서 persist**된다.

저장 위치:

- 사용자 프로필 설정에 Workspace별로 선호 뷰 저장
- 다음 방문 시 마지막 선택 뷰로 시작

다른 Workspace는 독립적으로 관리 (WS A는 Pipeline, WS B는 Grid 가능).

#### 규칙 3: 뷰 전환 버튼은 필터 영역에 배치

Agent 목록 상단의 검색·필터 영역 우측 끝에 뷰 전환 버튼 3개를 배치.

```
[🔍 Search...] [Status ▼] [Sort ▼]          [▦] [☰] [⫼]
```

활성 뷰는 시각적으로 강조(배경색 또는 테두리).

#### 규칙 4: 뷰별 정보 구성은 독립적으로 최적화

각 뷰는 같은 데이터를 다른 방식으로 보여주되, **뷰별로 표시 정보를 최적화**한다. 동일 데이터를 강제로 모든 뷰에 욱여넣지 않는다.

자세한 내용은 §4 "뷰별 명세" 참조.

#### 규칙 5: Team Metrics는 뷰와 무관하게 고정

페이지 상단의 Team Metrics(대화량, CSAT, 알림 등 팀 대시보드 영역)는 **모든 뷰에서 동일하게** 최상단에 표시한다. 뷰 전환은 Agent 리스트 영역에만 영향을 준다.

#### 규칙 6: 뷰 간 전환은 즉시

뷰 전환에 로딩·딜레이가 없어야 한다. 같은 데이터를 다르게 그리는 것뿐이므로, 클라이언트 사이드에서 즉시 리렌더링.

## 🧱 4. 뷰별 명세

### 4.1 Grid 뷰 (기본)

ADR-001, 002에서 정의한 Agent 카드를 그대로 사용.

**레이아웃**: 반응형 그리드 (3~4열)

**한 카드 = 한 Agent**

**카드에 담기는 정보**:

- 복합 상태 라벨 (최상단, 최대 3개)
- Agent 이름·아이콘·설명
- Production 기준 핵심 지표
- Dev/Staging 축약 정보
- 최종 수정 메타

**최적 사용 맥락**:

- "우리 팀에 어떤 Agent들이 있지?" (탐색)
- 팀장이 전반 상태 파악
- 신규 사용자의 기본 경험

### 4.2 List 뷰

테이블 형태로 Agent를 한 줄씩 표시.

**레이아웃**: 정렬 가능한 테이블

**컬럼 구성**:

- Name (이름 + 아이콘)
- Composite State (복합 상태 라벨)
- Prod Version / Conversations / CSAT
- Dev / Staging Version
- Last Edit
- Actions (⋯)

**최적 사용 맥락**:

- Agent 개수가 많음 (15개+)
- 특정 지표로 정렬해서 비교
- 스크롤 없이 많은 Agent를 훑기

### 4.3 Pipeline 뷰 (핵심 추가안)

환경을 컬럼으로, Agent를 카드로 배치한 칸반 보드.

#### 4.3.1 레이아웃

```
┌─ DEVELOPMENT (3) ─┬─ STAGING (1) ─┬─ PRODUCTION (2) ─┐
│                   │               │                   │
│ [Agent 카드]      │ [Agent 카드]  │ [Agent 카드]      │
│ [Agent 카드]      │               │ [Agent 카드]      │
│ [Agent 카드]      │               │                   │
│                   │               │                   │
└───────────────────┴───────────────┴───────────────────┘
```

- 3개 컬럼 동일 너비
- 각 컬럼 상단에 환경명 + 카드 개수
- 컬럼 내에서 카드는 세로 배치
- 환경 내 정렬: 기본은 **최종 수정 시각 최신순**, 커스텀 가능

#### 4.3.2 카드 표시 정보 (환경별 차등)

같은 Agent라도 **어느 컬럼에 있느냐에 따라** 카드가 보여주는 정보가 다르다.

**Development 컬럼 카드**:

| 요소          | 내용                   |
| ------------- | ---------------------- |
| 이름 + 아이콘 | Agent 식별             |
| 현재 Dev 버전 | v0.42                  |
| 작업 상태     | "편집 중 (2h ago)"     |
| 작업자        | "by Jiyong"            |
| 액션          | `→ Promote to Staging` |

**Staging 컬럼 카드**:

| 요소              | 내용                      |
| ----------------- | ------------------------- |
| 이름 + 아이콘     | Agent 식별                |
| 현재 Staging 버전 | v0.41                     |
| QA 진행 상태      | "2 days in QA"            |
| 테스트 결과       | "12/15 tests passed"      |
| 액션              | `→ Promote to Production` |

**Production 컬럼 카드**:

| 요소           | 내용              |
| -------------- | ----------------- |
| 이름 + 아이콘  | Agent 식별        |
| 현재 Prod 버전 | v0.38             |
| 핵심 지표      | 💬 12.4K · 😊 4.6 |
| 알림           | ⚠ 2 alerts        |
| 건강 상태      | 🟢 Healthy        |
| 액션           | `↓ Rollback`      |

각 환경에서 **실제 중요한 정보가 다르다**는 점이 이 뷰의 강점이다.

#### 4.3.3 같은 Agent의 여러 컬럼 등장 처리

Support Bot이 3개 컬럼에 동시에 나타날 수 있다. 혼동을 막기 위한 시각 장치:

1. **시각적 동일성 신호**: 같은 Agent는 같은 아이콘·색상 테마
2. **호버 하이라이트**: 한 카드에 마우스 호버 시, 같은 Agent의 다른 컬럼 카드도 함께 하이라이트
3. **연결 표시 (선택)**: 컬럼 간에 얇은 연결선으로 같은 Agent임을 암시 (복잡해질 수 있으니 선택적)
4. **이름 필터링**: Agent 이름 클릭 시 해당 Agent의 모든 환경 카드만 필터링

#### 4.3.4 드래그 앤 드롭 동작

Jira처럼 카드를 드래그할 수 있다. 단, **바로 이동이 아닌 확인 단계 필수**.

- Dev 카드를 Staging 컬럼으로 드래그 → **Promote 다이얼로그** 오픈 → 확인 후 실행
- Prod 카드를 Staging 쪽으로 드래그 → **Rollback 다이얼로그** 오픈
- 드래그로 역방향(Prod → Dev) 이동은 허용하지 않음 (의미상 불가능)

**드래그 피드백**:

- 드래그 중: 원본 카드는 반투명, 드롭 가능 컬럼은 하이라이트
- 드롭 후: 로딩 스피너와 함께 다이얼로그 오픈

#### 4.3.5 빈 컬럼 처리

특정 환경에 Agent가 0개인 경우:

```
STAGING (0)
─────────────
(이 환경에는
 배포된 Agent가
 없습니다)
```

빈 상태는 중앙 회색 텍스트로 표시. 컬럼은 유지 (너비 축소하지 않음).

#### 4.3.6 최적 사용 맥락

- 개발자·QA가 파이프라인 작업 중
- 팀장이 "Staging에 병목이 있는지" 점검
- 릴리즈 관리자가 배포 일정 계획
- 환경별 부하 파악

## 🔄 검토한 대안들 (Alternatives Considered)

### 대안 A: Pipeline 단독 (Grid 폐기) ❌

Pipeline을 기본이자 유일한 뷰로 사용.

**장점**:

- 제품의 파이프라인 본질 극대화
- UI 일관성 (하나의 뷰만 유지)
- 구현·유지보수 단순

**단점**:

- **Agent 중심의 사용 맥락 상실**: "우리 팀 Agent 목록" 같은 단순 질문에 과한 레이아웃
- **Agent가 많아지면 카드 폭발**: 10개 Agent × 3환경 = 30개 카드, 스크롤 지옥
- **Agent 단위 작업(Rename, Archive, Delete)이 혼란**: 3개 카드가 모두 사라지는 동작이 직관적이지 않음
- **지표 밀도 낮음**: 각 카드가 작아 Prod 지표를 충분히 표시 어려움

**기각 이유**: Workspace Home의 가장 빈번한 사용 목적(Agent 탐색·관리)에 불리. Pipeline은 특정 맥락에서만 강점.

### 대안 B: Grid 단독 (Pipeline 미도입) ❌

Pipeline 개념을 도입하지 않고, Grid에서 모든 요구를 해결.

**장점**:

- 단일 뷰로 인지 부하 낮음
- 구현 단순
- 기존 ADR-001, 002 그대로 유효

**단점**:

- **파이프라인 흐름의 시각적 강조가 약함**: Grid에서는 환경이 카드 내 정보로만 표시
- **환경별 부하 파악 어려움**: "Staging에 몇 개 있지?"를 카드 하나하나 봐야 답 가능
- **개발자·QA 페르소나의 작업 시나리오에 불리**: 이들은 특정 환경에 집중하는데, Grid는 환경 필터를 거쳐야 함

**기각 이유**: 제품의 핵심 가치(환경 파이프라인)를 UI로 직접 표현할 기회를 놓침. 질문자의 직관(칸반 스타일)이 실제로 가치 있는 관점임을 인정.

### 대안 C: Grid 기본 + Pipeline 탭으로 분리 △

Grid는 Workspace Home에, Pipeline은 별도 탭("Pipeline" 또는 "Releases")으로 분리.

```
Workspace Home | Pipeline | Members | Settings
```

**장점**:

- 두 뷰의 역할이 완전히 분리됨
- Pipeline이 독립된 기능으로 존재감

**단점**:

- **같은 데이터를 두 탭으로 분리하면 정보 파편화**: 사용자가 어디 가서 뭘 볼지 매번 결정
- **뷰 전환 비용 증가**: 탭 이동은 뷰 전환보다 무거움
- **Team Metrics 중복 또는 분리**: 두 탭 모두에 대시보드 필요?

**기각 이유**: 뷰 모드 전환이 탭 전환보다 가볍고 맥락 유지에 유리.

### 대안 D: 사용자 역할별 기본 뷰 자동 선택 △

사용자 Role에 따라 기본 뷰를 자동 결정.

- Admin / Owner → Grid
- Editor (개발자) → Pipeline
- QA → Pipeline (Staging 컬럼 강조)
- Viewer → List

**장점**:

- 각 페르소나에 최적화된 첫 경험

**단점**:

- **자동 분기의 예측 불가능성**: "왜 내가 보는 화면과 동료가 보는 화면이 다르지?"
- **팀원 간 소통 마찰**: "Pipeline에서 보면…" "어느 화면?"
- Role과 선호 뷰가 항상 일치하지 않음

**기각 이유**: 명시적 사용자 선택이 자동 추론보다 항상 투명하다.

### 대안 E: 단일 뷰에 환경 필터만 추가 △

Grid 단일 뷰를 유지하되, "환경 필터" 드롭다운으로 특정 환경에 배포된 Agent만 보기.

**장점**:

- 구현 가장 간단
- Grid 유지

**단점**:

- **파이프라인 흐름 시각화 불가**: 필터는 한 환경씩 보기만 할 뿐, 환경 간 관계를 못 보여줌
- Pipeline 뷰의 핵심 가치(컬럼 비교)를 제공 못함

**기각 이유**: 필터는 Pipeline 뷰의 "집중" 측면은 해결하지만 "흐름" 측면은 해결 못함. 부분적 해결책.

## 🎯 결정의 근거 (Rationale)

### 1. 두 관점 모두 유효하며 상호보완적

본 결정의 가장 중요한 통찰은 **"Agent 중심"과 "환경 중심"이 양자택일이 아니라는 점**이다. 두 관점은 각자 다른 질문에 답한다.

| 관점                 | 답하는 질문                     |
| -------------------- | ------------------------------- |
| Agent 중심 (Grid)    | 이 팀의 Agent 포트폴리오는?     |
| 환경 중심 (Pipeline) | 이 팀의 배포 파이프라인 상태는? |

두 질문 모두 팀 운영에서 중요하며, 상황에 따라 다르게 필요하다. 하나를 버리는 것은 사용자에게 손해.

### 2. Jira·Linear·GitHub Projects의 성공 사례

산업 표준 툴들이 이미 증명한 패턴이다.

- Jira: Backlog / Board / List / Calendar / Timeline 다중 뷰
- Linear: List / Board / Timeline
- GitHub Projects: Table / Board / Roadmap

사용자들은 이미 "같은 데이터를 다른 뷰로 보기"에 익숙하다. 학습 비용이 낮다.

### 3. 기본값 선택의 신중함

Grid를 기본값으로 하되 Pipeline을 제공하는 이유:

- **첫인상의 중요성**: 신규 사용자가 Pipeline을 먼저 보면 "환경 파이프라인을 이해하기 전에는 이 제품이 복잡해 보임". Grid는 더 친숙하고 Agent 개념부터 학습 가능.
- **범용성**: Agent 탐색·관리는 모든 사용자가 하지만, 파이프라인 작업은 특정 페르소나가 함. 다수에 맞춰 기본값 설정.
- **Pipeline은 옵트인**: 필요한 사람이 전환하면 됨. 전환 비용(버튼 하나)은 낮음.

### 4. 뷰별 정보 최적화의 힘

각 뷰가 서로 다른 정보를 강조할 수 있다는 점이 이 결정의 실질적 가치다.

- Grid에서는 Agent 전체 정보를 압축 표시
- Pipeline에서는 환경별로 다른 정보를 강조 (Dev=편집 상태, Staging=QA 결과, Prod=지표)

같은 카드를 모든 뷰에 쓰면 이 최적화를 못 함.

### 5. 드래그 기반 Promote의 자연스러움

Pipeline 뷰의 숨은 가치: 칸반 레이아웃은 드래그 인터랙션을 자연스럽게 만든다. Dev → Staging 드래그가 **"승격"의 은유**로 직관적이다.

단, 드래그만으로 실행되지 않고 확인 다이얼로그를 거치므로 실수 위험은 통제됨 (ADR-002의 환경 Promote 안전장치 원칙과 일치).

### 6. 확장성

향후 다른 화면(Organization Home, Agent 검색)에도 같은 3-way 뷰 패턴 적용 가능. 제품 전반의 일관된 언어가 됨.

## 🔀 결과 및 영향 (Consequences)

### 긍정적 영향

- **모든 페르소나가 자기 맥락에 맞는 뷰 선택 가능**
- **제품의 파이프라인 본질이 UI 옵션으로 존재감**
- **업계 표준 패턴(다중 뷰)과의 정합성**
- **향후 확장 여지**: Organization Home, Agent 검색 등에 동일 패턴 적용 가능
- **기본값(Grid) 유지로 신규 사용자 학습 곡선 통제**

### 부정적 영향 (트레이드오프)

- **구현 복잡도 증가**: 3개 뷰 각각의 레이아웃·인터랙션 구현
- **디자인 유지보수 비용**: 3개 뷰의 일관성 관리
- **테스트 범위 확대**: 각 뷰별 시나리오 테스트
- **사용자 설정 저장소 필요**: 뷰 선호도 persist 로직
- **드래그 앤 드롭 구현 난이도**: Pipeline 뷰의 드래그 인터랙션

### 단계적 도입 전략 제안

MVP에서 3개 뷰를 동시에 런칭하면 리스크가 크다. 다음 순서로 단계 도입 권장.

**Phase 1 (MVP)**:

- **Grid 뷰만** 완성하여 출시
- 뷰 전환 UI는 숨김 (향후 확장 준비)

**Phase 2 (사용자 피드백 기반)**:

- **Pipeline 뷰** 추가 (가장 가치 있는 추가분)
- 뷰 전환 토글 노출
- 드래그 앤 드롭 포함

**Phase 3 (운영 안정화 후)**:

- **List 뷰** 추가 (Agent 많은 대규모 고객 대응)

이 순서는 본 ADR의 결정을 **단번에 구현하지 않고 점진적으로 실현**하는 방식이다. 각 단계는 별도의 스프린트나 릴리즈로 처리 가능.

### 후속 작업 필요

1. **WORKSPACE_HOME_INFO_GUIDE.md 업데이트**
   - 뷰 모드 개념 추가
   - 각 뷰별 정보 구성 명세

2. **PIPELINE_VIEW_SPEC.md 신규 작성**
   - Pipeline 뷰의 상세 명세
   - 카드 컴포넌트 환경별 차등 내용
   - 드래그 앤 드롭 인터랙션 규칙

3. **USER_PREFERENCES_SPEC.md 신규 작성**
   - 뷰 선호도 저장 방식
   - Workspace별 독립 관리 규칙

4. **디자인 토큰 확장**
   - 각 뷰의 컬럼/카드 스타일 정의
   - 드래그 상태의 시각적 피드백

5. **PRD.md §6 설계 원칙 추가**
   - "같은 데이터, 다른 관점 — 뷰 모드 제공"을 핵심 원칙에 포함

### 모니터링 지표

이 결정이 옳았는지 검증할 지표.

- **뷰 모드별 사용률**: Grid %, List %, Pipeline %
- **뷰 전환 빈도**: 사용자가 실제로 전환하는가, 한 뷰에만 머무는가
- **페르소나별 뷰 선호도**: 개발자가 Pipeline 선호? QA가 Pipeline 선호?
- **Pipeline에서의 드래그 Promote 성공률**: 실수 없이 실행되는가
- **작업 완료 시간**: 같은 작업을 Grid vs Pipeline에서 수행할 때

### 위험 요소

- **Pipeline 뷰 사용률이 저조할 가능성**: 구현 비용 대비 ROI 낮을 수 있음 → Phase 2로 지연하여 MVP 후 사용자 피드백 기반 판단
- **뷰 개수 폭발**: 향후 Calendar, Timeline, Dependency 등 추가 요구 가능 → 본 ADR에서 3개로 제한, 추가 시 ADR 개정 필요
- **모바일에서 Pipeline 뷰의 어려움**: 3컬럼 칸반은 좁은 화면에 부적합 → 모바일에서는 자동으로 Grid 또는 List로 폴백

## 🔗 다른 결정들과의 관계

### ADR-001, ADR-002와의 관계

- **ADR-001** (Prod 중심 표시): Grid 뷰의 카드 설계 원칙. Pipeline 뷰에서도 Prod 컬럼에서 지표가 강조되는 형태로 일관성 유지.
- **ADR-002** (복합 상태 라벨): Grid 뷰에서 핵심. Pipeline 뷰에서는 **환경별로 카드가 분산**되므로 복합 상태 라벨이 불필요 (카드가 속한 컬럼 자체가 상태 의미를 가짐).

세 ADR은 서로 배타적이지 않고 **상호 보완**한다.

### 향후 ADR에 미치는 영향

- **Organization Home의 구조**: 같은 3-way 뷰 패턴 적용할지 결정 필요
- **Promote 플로우 UX**: Pipeline 뷰의 드래그 기반과 Grid 뷰의 버튼 기반이 동일한 다이얼로그로 수렴하도록 설계
- **알림 시스템**: "Staging에서 5일째 대기" 같은 알림이 Pipeline 뷰에서 어떻게 표현될지
